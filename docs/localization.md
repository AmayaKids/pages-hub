# Локализация (i18n)

## Два независимых уровня

1. **Глобальный уровень** — `@nuxtjs/i18n` в `nuxt.config.ts`. Список из 9 языков, `strategy: 'prefix'`
   (все роуты живут под `/:locale/...`), `defaultLocale: 'en'`. Это список **всех переводов, которые
   физически существуют** в проекте (`i18n/locales/*.json`). Он никогда не меняется по хосту — Nuxt i18n
   генерирует локализованные роуты на этапе сборки, без знания о хосте запроса.
2. **Per-host уровень** — `shared/hostLandings.ts` → `HOST_CONFIGS[host].locale`. Это **runtime**-слой,
   который поверх глобального списка решает, сколько из этих языков доступно на конкретном
   домене/поддомене и какой из них дефолтный.

Важно: per-host конфиг может только **сужать** глобальный список языков, но не может добавить язык, для
которого нет перевода — сначала язык должен быть добавлен в `nuxt.config.ts` → `i18n.locales` и получить
файл перевода.

## `/a/**` — не трогаем per-host логикой

Пути `/a/**` (`pages.amayakids.com`) всегда используют **полный** глобальный список языков и глобальный
дефолт (`en`), независимо от `HOST_CONFIGS`. Это сделано специально, чтобы не сломать существующий
функционал подарочных карт/инструкций. Если нужно ограничить языки и для `/a/**` — это отдельная задача,
затрагивающая `nuxt.config.ts` напрямую, а не `HOST_CONFIGS`.

## ⚠️ Почему нет режима "локализация полностью выключена" (без префикса вообще)

Изначально в этом слое была задумана опция `{ enabled: false }` — страница без `/:locale`-префикса
вообще. **На практике это несовместимо с тем, как работает `@nuxtjs/i18n` при `strategy: 'prefix'`.**

`strategy: 'prefix'` — это глобальная настройка модуля, а не per-page/per-host. При ней i18n **сам**,
независимо от `detectBrowserLanguage` и от любой нашей логики, всегда редиректит непрефиксованный `/` на
`/${defaultLocale}` — это часть его базового механизма роутинга, а не опциональная фича, которую можно
выключить для одного хоста. Раньше `/` дополнительно был прописан в `routeRules` как `prerender: true` —
статическая версия страницы, испечённая один раз при сборке без реального `Host`, что дополнительно
усугубляло проблему (см. ниже).

Если для хоста в `HOST_CONFIGS` включить `{ enabled: false }` (обрезать `/xx`-префикс обратно на `/`), то
получается вечная борьба: i18n редиректит `/` → `/en`, наша логика режет `/en` → `/`, i18n снова
редиректит `/` → `/en`, и так по кругу — **бесконечный редирект-луп** (именно это и произошло в проде на
`l2.amayasoft.uz`).

**Решение:** вместо "выключить локализацию", для хоста, где нужен только один язык без видимого
переключения, задать **список из одного языка**:

```ts
'l1.amayasoft.uz': {
  pageKey: 'amayasoft-uz-l1',
  locale: { locales: ['ru'], defaultLocale: 'ru' }
}
```

Тогда `/` один раз редиректит на `/ru` (это делает сам i18n) и там и остаётся — обрезать что-то обратно
не нужно, зацикливания в принципе не может быть. Единственное отличие от "настоящего" отсутствия
локализации — префикс `/ru` виден в адресной строке.

## Конфигурация: `shared/hostLandings.ts`

```ts
export const GLOBAL_LOCALES = ['en', 'ru', 'de', 'es', 'it', 'pt', 'fr', 'sv', 'nl'] as const
export const GLOBAL_DEFAULT_LOCALE: LocaleCode = 'en'

export interface LandingLocaleConfig {
  locales: readonly LocaleCode[]
  defaultLocale: LocaleCode
}
```

Каждый хост в `HOST_CONFIGS` содержит поле `locale`:

```ts
'l1.amayasoft.uz': {
  pageKey: 'amayasoft-uz-l1',
  locale: { locales: ['en', 'ru'], defaultLocale: 'ru' }
}
```

- `locales` — какие языки доступны на этом хосте. Должны быть подмножеством `GLOBAL_LOCALES`.
- `defaultLocale` — на какой язык редиректить, если:
  - в пути нет локали вообще (`/` → `/{defaultLocale}`, это делает сам i18n);
  - запрошенный язык не входит в `locales` для этого хоста (например, зашли на `/de`, а `de` не
    поддерживается на этом поддомене → редирект на `defaultLocale`).
- Один язык в массиве (`locales: ['ru']`) — практический эквивалент "локализация не нужна": пользователь
  всегда просто видит `/ru`, переключения языков нет.

### Хост не указан в `HOST_CONFIGS`

`getHostLocaleConfig()` возвращает "открытую" конфигурацию по умолчанию — полный `GLOBAL_LOCALES` и
`GLOBAL_DEFAULT_LOCALE`. Так ведёт себя, например, `pages.amayakids.com` для любых путей за пределами
`/a/**` (в теории; на практике у него просто нет лендинга на `/`, так что там будет 404 от диспетчера, а
не редирект).

## Как это применяется в middleware

### `app/middleware/i18n-redirect.global.ts` (сервер + клиент)

Псевдо-алгоритм на каждую навигацию:

1. Если путь — статический ассет (`/assets`, `/_nuxt`, `favicon.ico`, ...) — пропустить.
2. Отделить возможный 2-буквенный локаль-префикс от пути (`/ru/l1` → локаль `ru`, остаток `/l1`).
3. Если остаток пути — это `/a` или `/a/**`:
   - применить **глобальные** правила (весь `GLOBAL_LOCALES`, дефолт `en`), независимо от хоста;
4. Иначе (страница-лендинг домена/поддомена):
   - получить `useAppHost()` → `getHostLocaleConfig(host)`;
   - если префикса нет ИЛИ он не входит в `locales` хоста → 301 на
     `/{defaultLocale для хоста}{остаток пути}`.

Важно: сам факт "префикса нет" (`/`) в реальности почти никогда не долетает до этой ветки —
`@nuxtjs/i18n` перехватывает `/` раньше и сам редиректит на `/${GLOBAL_DEFAULT_LOCALE}` (см. секцию выше).
Эта ветка страхует остальные случаи (например, прямой заход на не поддерживаемую хостом локаль).

### `server/middleware/host-landing.ts` (только сервер)

Отвечает за старые ссылки вида `/:locale/:slug` (например `/ru/l1`, когда `l1` — слаг поддомена) —
приводит их к каноническому виду одним редиректом:

- находит слаг для хоста (`getLandingSlug`);
- если путь совпадает с `/:locale/{slug}` — смотрит `getHostLocaleConfig(host)`:
  - запрошенная локаль валидна для хоста → редирект на `/{locale}`;
  - локаль не валидна для хоста → редирект сразу на `/{defaultLocale хоста}` (не на
    `/{запрошенная локаль}`, чтобы не было двух редиректов подряд).

## `routeRules['/']` — почему `/` НЕЛЬЗЯ пререндерить

`/` больше не помечен как `prerender: true` в `nuxt.config.ts`. Раньше это было так, но привело к
продовому багу: пререндеринг печёт статический HTML **один раз при сборке**, без реального `Host`, и
Nitro потом отдаёт этот же файл **всем хостам одинаково**. Раз наша страница-диспетчер (`app/pages/index.vue`)
и её локали зависят от `Host`, а статика в принципе не может ветвиться по хосту — держать `/` статикой
означало "заморозить" её поведение на момент сборки для абсолютно всех доменов. Комбинация с
host-специфичными языковыми правилами и была прямой причиной бесконечного редирект-лупа. `/` должен
рендериться динамически на каждый запрос.

## Как изменить языки для домена/поддомена — шаги

1. Открыть `shared/hostLandings.ts`.
2. Найти нужный хост в `HOST_CONFIGS`.
3. Отредактировать `locale`:
   - сузить список — поменять массив `locales` (например `['en', 'ru']`);
   - сменить дефолтный язык — поменять `defaultLocale` (должен входить в `locales`);
   - "один язык / без переключения" — оставить в `locales` только один код.
4. Если нужно добавить язык, которого ещё нет в проекте:
   - добавить в `nuxt.config.ts` → `i18n.locales` (`{ code, iso, file }`);
   - создать файл перевода `i18n/locales/{code}.json`;
   - добавить код языка в `GLOBAL_LOCALES` в `shared/hostLandings.ts`;
   - только после этого его можно указывать в `locales` конкретного хоста.
5. Прогнать `pnpm lint`, `pnpm typecheck`, `pnpm build` — типы `LocaleCode` не дадут указать
   несуществующий код языка.

## Проверка вручную (curl)

```bash
# язык не поддерживается на хосте -> редирект на дефолтный для хоста язык
curl -sI -H "Host: pages.amayakids.com" -H "X-Forwarded-Host: l1.amayasoft.uz" \
  http://localhost:3000/de | grep -i location

# полный цикл с редиректами: должно быть 1-2 редиректа и 200, БЕЗ петли
curl -s -o /dev/null -w "code:%{http_code} redirects:%{num_redirects}\n" -L --max-redirs 5 \
  -H "Host: pages.amayakids.com" -H "X-Forwarded-Host: l1.amayasoft.uz" http://localhost:3000/

# /a/** всегда на глобальных правилах, независимо от хоста выше
curl -sI http://localhost:3000/a/gift-card/test | grep -i location
```

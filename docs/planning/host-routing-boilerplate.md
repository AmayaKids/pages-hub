# Boilerplate при добавлении страниц хостам

**Статус:** обсуждали 2026-08-25, решение не принято, в коде ничего не меняли. Текущая рабочая схема
описана в [domains-and-subdomains.md](../domains-and-subdomains.md) → «Как добавить доп. страницу для
хоста (не `/`)».

## Проблема

Чтобы добавить хосту одну страницу (например `/payment-result` на `l1.amayasoft.uz`), сейчас нужно **два**
файла:

1. сама страница — `app/pages/(amayasoft.uz)/(subdomains)/l1/payment-result/index.vue`;
2. файл-диспетчер на реальном пути — `app/pages/payment-result/index.vue`, с `definePageMeta({ i18n: false })`
   и вызовом `resolveHostPage()`.

Первый файл роутингом вообще не виден: папки `(amayakids.com)` и `(amayasoft.uz)` исключены из авто-скана
через `pages.pattern` в `nuxt.config.ts`. Исключение сделано, чтобы route-группы (папки в скобках не влияют
на URL) не конфликтовали за один и тот же путь: `(amayasoft.uz)/(subdomains)/l1/payment-result` и
`.../l2/payment-result` оба дают `/payment-result`.

Симптом, из-за которого всё это всплыло: страница создана, но `/payment-result` отдаёт 404 — потому что
роут для неё не регистрируется вообще, и запрос проваливается в `[lng]/index.vue`, где `validate` не
пропускает `payment-result` как код языка.

Хотелось бы: **положил файл в папку хоста — роут появился**, без второго файла.

## Что проверено по исходникам (не по памяти)

Это главное, что стоит сохранить — на этих фактах строятся варианты ниже.

1. **Таблицу роутов можно фильтровать по хосту в рантайме.**
   `app/router.options.ts` → функция `routes()` вызывается в
   `node_modules/nuxt/dist/pages/runtime/plugins/router.js:36`
   (`const routes = routerOptions.routes ? await routerOptions.routes(_routes) ?? _routes : _routes`)
   — то есть **до** `createRouter()` и **внутри** `defineNuxtPlugin.setup(nuxtApp)`. Плагины исполняются
   через `nuxtApp.runWithContext(() => plugin(nuxtApp))`
   (`node_modules/nuxt/dist/app/nuxt.js:142`), значит внутри `routes()` доступны Nuxt-композаблы, включая
   `useAppHost()` / `useRequestHeaders()`. На сервере это выполняется **на каждый запрос**, на клиенте —
   один раз при старте. Функция может быть `async`.

2. **Из (1) следует, что коллизии путей можно не предотвращать, а разрешать.**
   Если оставить host-папки в авто-скане, в build-time таблице будут дубликаты путей (`/payment-result` от
   l1 и от l2), но если до `createRouter()` отфильтровать всё, что не принадлежит текущему хосту, конфликта
   физически не возникнет. То есть `pages.pattern`-исключения, `HostLandingRouter` и файлы-диспетчеры
   становятся ненужными.

3. **`@nuxtjs/i18n` работает только на build-time и рантайм-роутер не трогает.**
   Локализованные варианты роутов он генерирует хуком `pages:resolved`/`pages:extend`
   (`node_modules/@nuxtjs/i18n/dist/module.mjs:1014`). Значит рантайм-фильтр из (1) работал бы поверх уже
   локализованной таблицы — и per-host набор языков можно было бы фильтровать там же, вместо текущего
   `[lng]/index.vue` + `validate`.

4. **Почему нужен `i18n: false` на диспетчере (актуально и для текущей схемы).**
   При `strategy: 'prefix'` i18n забирает под себя каждый путь, который не помечен
   `definePageMeta({ i18n: false })`, и требует локаль-префикс. Проверяется по сгенерированному
   `.nuxt/i18n-route-resources.mjs`: там есть массивы `localizedPaths` и `disabledPaths` — новый путь,
   попавший в `localizedPaths` вместо `disabledPaths`, работать на голом URL не будет. Полезный приём для
   отладки подобных 404.

5. **Дев-сервер не всегда подхватывает новый top-level роут по HMR.** При появлении новой папки в
   `app/pages/` пришлось перезапускать `pnpm dev` (с `rm -rf .nuxt`), иначе роут отсутствовал в таблице и
   запрос уходил в `[lng]`. Если страница «точно есть, но 404» — сначала перезапуск, потом дебаг.

## Рассмотренные варианты

### A. Как сейчас: страница + явный диспетчер

Плюсы: нулевая магия, всё явно, любой Nuxt-фича работает на уровне диспетчера, легко дебажить.
Минусы: два файла на страницу; `definePageMeta` на самой странице хоста не работает (она — обычный
компонент, не page); про `i18n: false` на диспетчере легко забыть и получить загадочный 404.

### B. Рантайм-фильтр роутов по хосту (`pages:extend` + `router.options.ts`)

Убрать исключения из `pages.pattern`; в `pages:extend` пометить страницы из host-групп `meta.host`
(и сделать уникальными `name`, чтобы vue-router не ругался на дубликаты); в `app/router.options.ts`
оставить только роуты текущего хоста + роуты без `meta.host` (глобальные, `/a/**`).

Плюсы: «просто создай файл» — то, чего хотелось; **удаляет** `HostLandingRouter.vue`,
`app/pages/index.vue`, `app/pages/[lng]/index.vue`, `app/composables/useHostPage.ts`, все диспетчеры и
исключения `pages.pattern` — суммарно кода меньше, чем сейчас; сохраняет полный vue-router: динамические
сегменты, `definePageMeta`, layouts, middleware, `validate` **на самих страницах хоста**; заодно позволяет
сделать per-host локали настоящими роутами (см. факт 3) и выкинуть хак с `validate` по `/^[a-z]{2}$/`.

Минусы: рантайм-хирургия над таблицей роутов — при ошибке в фильтре симптом «мистический 404», который
дебажить сложнее отсутствующего файла; пререндер host-страниц становится невозможен в принципе (сейчас
`/` и так не пререндерится, так что скорее фиксация текущего положения); нужно следить, чтобы SSR и клиент
считали хост одинаково (уже решено в `useAppHost()`, включая `.loc`-суффикс для локальной разработки).

### C. Один catch-all `[...slug].vue` + glob-реестр компонентов

Вся маршрутизация хостов в одном файле: парсим путь, при необходимости снимаем локаль-префикс по конфигу
хоста, достаём компонент из `import.meta.glob` по ключу `host + path`.

Плюсы: один файл на весь механизм, ноль boilerplate на страницу.
Минусы: теряются динамические сегменты внутри лендингов (`payment-result/[orderId].vue` пришлось бы
матчить руками, фактически свой роутер) и `definePageMeta` на страницах; `[lng]` придётся удалить и
разбирать локали внутри catch-all, т.к. `:lng` специфичнее `:slug(.*)` и перехватывал бы пути первым.

### D. Кодогенерация диспетчеров локальным Nuxt-модулем

Модуль сканирует host-папки и на build-time генерирует те же диспетчеры в `.nuxt` (через `addTemplate` +
`pages:extend`).

Плюсы: тоже «просто создай файл», но без рантайм-магии — пререндер и отладка проще, чем в B.
Минусы: build-time магия вместо рантайм-магии; `definePageMeta` на самой странице хоста по-прежнему не
работает (как в A); свой модуль надо поддерживать.

### E. Отдельные приложения / Nuxt-слои на домен

Свой деплой на каждый хост, никакой диспетчеризации вообще.
Плюсы: концептуально чище всего. Минусы: инфраструктурная цена, дублирование общего кода, отдельные
пайплайны.

## Открытые вопросы (на них нужен ответ, чтобы выбрать)

1. Сколько страниц реально будет у хостов: 1–3 (тогда boilerplate терпим, вариант A) или 5+ (тогда
   осмысленны B/D)?
2. Нужны ли динамические сегменты внутри лендингов (`/order/[id]`) — если да, вариант C отпадает.
3. Нужен ли `definePageMeta` (свой layout / middleware / `validate`) на самих страницах хоста — если да,
   проходит только B.
4. Будет ли один и тот же путь на нескольких хостах с разным содержимым?
5. Нужен ли когда-нибудь пререндер/SSG для host-страниц — если да, B под вопросом.
6. Переводить ли per-host локали на настоящие роуты (убрать `[lng]` + `validate`) — сейчас это работает,
   но именно этот костыль дал 404 при добавлении страницы.
